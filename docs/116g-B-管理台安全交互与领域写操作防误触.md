## 1. 背景与问题

当前管理台交互层存在以下缺口（源码证据）：

1. **错误分类缺失**：`backend/admin/src/api/request.js` 只区分「`payload.code === 40101`」与「其它」，其余一律 `message.error(payload.msg)`。403（无权限/CSRF 失败/API 关闭）、429（限流）、5xx、断网无法被页面区分，页面无法给出确定性的 error/unauthorized 状态。
2. **会话清理边界过宽**：`src/api/auth.js` 的 `fetchUser` 在**任何失败**（含断网、5xx）都清空 `_cachedUser` 并返回 null；`src/App.jsx` 的 `RequireAuth` 随后把「网络失败」误判为「未登录」跳转 `/login`。违反「只有 401 才允许清理会话并跳转登录」。
3. **ResourcePage 状态不确定**：`src/pages/ResourcePage.jsx` 的 `ResourceTable` 只有 `loading` 布尔；列表请求失败后 `rows=[]`，空态与错误态无法区分；403 没有 unauthorized 呈现；无重试入口。
4. **竞态**：`loadList` / `loadConfig` 无请求序号守卫，快速切换资源、连续搜索、翻页时旧响应可覆盖新状态（detail 已有 `detailRequestRef`，list/config 没有）。
5. **写操作防误触缺失**：`submit` 无防重复提交（双击 onOk 会发两次写请求）；失败时虽然不会走到 success 分支，但缺少明确的处理中状态；删除 `Popconfirm` 文案为固定「确认删除这条记录？」，不含具体资源/记录标识。
6. **字段元数据消费不全**：只消费 `createOnly` / `required`；后端 config 若下发 `readonly`（服务端维护字段）没有对应消费策略。

## 2. 目标（本批对外口径）

- 把管理台请求失败精确分类为 8 类 + 2 类补充：**未认证、无权限、CSRF 失败、API 关闭、限流、网络失败、服务端错误、业务校验失败**（补充：资源不存在、未知错误）。
- **只有「未认证」清理会话并跳转登录**；403、CSRF、429、5xx、断网一律不登出。
- ResourcePage 建立确定性的 `loading / empty / error / unauthorized / api-disabled` 状态，互不混淆，错误可重试。
- 消除切换资源、搜索、分页、详情之间的旧响应覆盖新状态问题。
- 写操作具备：防重复提交、明确处理中状态、失败保留表单、成功后确定性刷新、删除/高风险操作精确确认、响应失败绝不展示成功提示。
- 支持后端 config 的 `readonly / createOnly / required` 字段元数据；**不在 Admin 内手写领域状态机镜像**。
- 页面可独立测试的请求错误、操作状态、字段可编辑性判断全部提取为纯函数。
- **Cookie、credentials、CSRF header、后端权限语义完全不变**；本文件描述的前端限制仅是体验层，**不是后端安全边界**（后端强制校验以 116e/116f 契约为准）。

## 3. 错误分类契约（以 116e/116f 后端实测行为为准）

后端事实源（只读盘点）：

- 信封：`{ code, msg, data, timestamp, traceId }`（`backend/src/utils/response.js`）。
- 业务码：`CODES` = 200 / 40001 / 40101 / 40301 / 40401 / 42901 / 50001 / 60001 / 60002（`backend/src/config/index.js` L241-250）。
- `fail(res, code, msg)` 的 HTTP 映射：40001→400、40101→401、40301→403、40401→404、42901→429、60001/60002→503、50001→500。
- CSRF 失败：`middleware/csrf.js` 返回 `40301` + msg `CSRF 校验失败：缺少 token` / `CSRF 校验失败：token 不匹配`。
- API 关闭：`middleware/apiControl.js` 返回 `40301` + msg `功能已关闭：<名称>`。
- 无权限：`middleware/auth.js` `requireRole` 返回 `40301` + msg `权限不足`。
- 限流：`middleware/apiControl.js` 返回 `42901` + msg `请求过于频繁，请稍后再试（<桶名>）`。

分类纯函数 `classifyRequestError({ payload, status, networkError })` 判定顺序（先业务码，后 HTTP 兜底）：

| category key | 中文名 | 判定 | 会话/登出行为 | 默认提示口径 |
|---|---|---|---|---|
| `unauthenticated` | 未认证 | `payload.code === 40101`，或 `status === 401` 且无有效 code | **唯一允许** clearSession + 跳 `/admin/login?reason=expired` | 会话已失效，请重新登录 |
| `forbidden` | 无权限 | `payload.code === 40301` 且 msg 不含 `CSRF 校验失败`、不以 `功能已关闭` 开头 | 不清会话、不登出 | 权限不足 |
| `csrf` | CSRF 失败 | `payload.code === 40301` 且 msg 含 `CSRF 校验失败` | 不清会话、不登出 | CSRF 校验失败，请刷新页面后重试 |
| `api-disabled` | API 关闭 | `payload.code === 40301` 且 msg 以 `功能已关闭` 开头 | 不清会话、不登出 | 功能已关闭（引用后端 msg） |
| `rate-limited` | 限流 | `payload.code === 42901` | 不清会话、不登出 | 请求过于频繁，请稍后再试 |
| `network` | 网络失败 | fetch 抛错（`networkError` 非空） | 不清会话、不登出 | 网络连接失败，请检查网络后重试 |
| `server` | 服务端错误 | `payload.code ∈ {50001, 60001, 60002}`，或 `status >= 500` | 不清会话、不登出 | 服务端异常，请稍后重试 |
| `validation` | 业务校验失败 | `payload.code === 40001`，或 `status === 400` | 不清会话、不登出 | 后端业务校验 msg |
| `not-found` | 资源不存在 | `payload.code === 40401`，或 `status === 404` | 不清会话、不登出 | 资源不存在 |
| `unknown` | 未知错误 | 以上均不命中（含 200 但信封不可解析） | 不清会话、不登出 | 请求失败，请稍后重试 |

行为契约（强测试锁定）：

1. 只有 `unauthenticated` 执行 `clearSession()` + `window.location.replace('/admin/login?reason=expired')`；其余类别**绝不**登出（含 403/CSRF/429/5xx/断网）。
2. 所有请求继续 `credentials: 'include'`；写请求（POST/PUT/PATCH/DELETE）继续注入 `X-CSRF-Token`（cookie 读取口径不变）。
3. 写请求**绝不自动重试**；GET/HEAD 支持调用方显式 `retries` 的受控重试（默认 0 次，行为与现状一致）。
4. 请求失败统一 `message.error` 呈现（未认证除外，直接跳转）；成功路径绝不因 catch 静默成功。
5. `fetchUser` 仅对 `unauthenticated` 清空 `_cachedUser`；网络/5xx/403/429 保留缓存（会话状态未知时不得破坏）。

## 4. ResourcePage 状态机与竞态治理

### 4.1 表格确定性状态（纯函数 `resolveTableState`）

输入 `{ configLoading, listLoading, error, rows, config }` → 输出唯一状态 key：

| 状态 | 进入条件 | 呈现 |
|---|---|---|
| `config-loading` | config 未就绪且 configLoading | 骨架加载 |
| `list-loading` | config 就绪且 listLoading | Table loading |
| `ready` | 无错误且 rows 非空 | 正常表格 |
| `empty` | 无错误且 rows 为空且 config 就绪 | 空态（区分「无数据」与「加载中」） |
| `error` | error 非空 | 错误态 + 重试按钮 |
| `unauthorized` | error.category === 'forbidden' | 「无权限」说明 + 刷新登录态按钮，不回退成普通 error |
| `api-disabled` | error.category === 'api-disabled' | 「功能已关闭」说明 |

错误态记录 `{ category, message, retryKey }`，重试按钮重放触发该次加载的相同参数（页/页大小/关键词）。

### 4.2 竞态治理（116g-B 审查整改 #1/#2 后口径）

- **配置与列表使用独立序号**（`createResourceLoadCoordinator` 内部 `configSeq` / `listSeq`，`src/policies/resourceLoadCoordinator.js`，页面与测试共用同一实现）：
  - 搜索/刷新/翻页只推进 `listSeq`，**不会**使在途配置请求失效——配置请求一定能完成，或被 `retry`/资源切换**确定性重发**，绝不永久停留在 config-loading；
  - 配置未就绪时 `loadList` 直接返回 `IGNORED_NO_CONFIG`（不发无配置请求）；页面同时在 UI 上禁用**搜索输入与搜索/刷新/新增按钮**——口径为「config 未就绪」而非仅「加载中」，覆盖**加载中/加载失败/尚无配置**三形态（`isConfigUnavailable(config)` 纯函数，PR #5 审查整改），错误态下仅保留重试入口；
  - 资源切换（`resetResource`）同时推进两个序号并清空配置——旧配置、旧列表在途响应全部失效（`STALE`）。
- **lastQuery 意图口径**：列表请求发起时即记录 `{page,pageSize,keyword}`（失败也记录），删除后 `refreshCurrentQuery()`、写成功后 `refreshAfterWrite({mode})`（创建回第 1 页、更新留当前页）一律以它为准，**不依赖组件闭包中可能过期的 pagination/keyword**。
- 详情请求独立序号（`detailSeqRef`）与配置/列表序号互不干扰；`ResourcePage` 层 `loadNames` 沿用 `nameSeqRef` 守卫。

### 4.3 写操作协调器（`createWriteOperation`，页面与测试共用同一实现）

116g-B 审查整改 #4：删除页面未消费的平行状态机模型（`reduceWriteOp`），改为 `src/policies/operationState.js` 导出的 `createWriteOperation({ perform, onSuccess, onFailure })`，由 `ResourcePage` 的提交与删除**真实消费**：

```
run(payload):
  busy 中再次 run → { duplicate: true }（不发起第二次写请求）
  执行 perform（唯一一次 POST/PUT/DELETE）
  成功 → onSuccess 恰好一次（组件内 = 关弹窗 + 成功提示一次 + 确定性刷新一次）
  失败 → onFailure 恰好一次（组件内 = 保留弹窗与表单、不弹成功、不刷新）
```

- `submitting`：Modal `confirmLoading`，onOk/删除按钮/关闭入口全部禁用；协调器 busy 守卫是双击拦截的硬保证（**只产生一次写请求**）。
- `failure`：Modal 保持打开、表单值保留（不 reset、不 destroy）、错误提示由请求层统一呈现；不弹成功提示。
- `success`：关闭 Modal → 成功提示**恰好一次** → 确定性刷新**恰好一次**（`refreshAfterWrite`：新建回第 1 页、更新留当前页；删除用 `refreshCurrentQuery`）；刷新失败不影响已成功的写结果提示（写已落库）。
- 删除确认（`Popconfirm`）标题必须包含**具体资源标题 + 记录 id + 首列表字段值**（`buildDeleteConfirmText` 纯函数），如 `确认删除「订单管理」#128（NO20260501…）？该操作不可恢复。`；确认按钮带 loading，删除进行中禁用行内按钮。

## 5. 字段元数据消费策略（纯函数，无领域状态机镜像）

`src/policies/fieldEditPolicy.js`：

| 元数据 | create 模式 | edit 模式 |
|---|---|---|
| `createOnly: true` | 可见、可编辑、可必填 | **隐藏**（不提交、不展示） |
| `readonly: true` | **隐藏**（服务端指派字段，创建时不可提供） | 可见但**禁用**（只读呈现） |
| `required: true` | 必填校验 | 必填校验 |

- 判定函数：`isFieldVisible(field, mode)`、`isFieldEditable(field, mode)`、`isFieldRequired(field, mode)`（`mode ∈ {'create','edit'}`）。
- 任何未声明的元数据一律按「可编辑」处理，**不推断、不镜像领域状态**；后端未下发 `readonly` 字段时行为与现状完全一致（当前 `resource.config.js` 无 readonly 字段，属未来兼容）。
- `normalizeInitial` 仅取「编辑模式可见」的字段（createOnly 已在其中被排除）。
- `buildSubmitPayload(values, fields, mode)`（审查整改 #3，ResourcePage 提交真实使用）：只提交当前模式**可见且可编辑**的字段——`readonly` 永不提交；`createOnly` 仅创建模式提交；隐藏字段与上一次弹窗残留值一律不进入请求 body。

## 6. 登录引导态决策（纯函数 `bootstrapSessionPolicy`）

`App.jsx` 的 `RequireAuth` 改用分类结果决策，`fetchUser` 的返回值由新入口 `bootstrapSession()` 提供：

| `/auth/me` 结果 | 决策 | 行为 |
|---|---|---|
| `code 200` | `ok` | 进入管理台 |
| `unauthenticated` | `expired` | clearSession + 跳 `/admin/login?reason=expired` |
| `network` / `server` / `rate-limited` / 其它 | `unavailable` | 保留会话缓存，展示「服务暂时不可用」+ 重试按钮，**不跳登录、不清会话** |
