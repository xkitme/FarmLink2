# 116b - 田园通大重构三档方案对比

> 状态：方案评审完成  
> 推荐结论：采用 B 档“渐进式领域重构”  
> 决策依据：[116a-大重构决策记录.md](116a-大重构决策记录.md)

## 1. 比较前提

- 当前时间为 2026-08-02，预计 9 月进入比赛验收。
- 主要开发者为 1 人，后续可能增加 2～3 人。
- 实际验收对象是评委，产品目标用户是农户。
- 正式交付端是 Flutter Android，Web 仅开发预览。
- 现有项目功能较多，但模块边界、测试和数据约束不足。
- 当前工作区还有约一万行未提交 116 删除改动，不能直接作为新基线。
- 比赛断网，不能让公网或本地大语言模型成为核心流程前置条件。

## 2. 三档方案总览

| 维度 | A 档：保守收敛 | B 档：渐进式领域重构 | C 档：全面重写 |
|---|---|---|---|
| 核心策略 | 修 P0、删入口、做视觉和演示打磨 | 保持技术栈，按领域逐步替换内部结构 | 重建 App、API、数据库和工程体系 |
| 预计投入 | 15～25 人日 | 35～50 人日 | 70～100+ 人日 |
| 9 月前可控性 | 高 | 中高，可通过截止线控制 | 低 |
| 评委第一印象 | 高 | 高 | 前期低、完成后高 |
| 业务闭环可信度 | 中 | 高 | 高 |
| 安全与数据一致性 | 只修阻断项 | 系统修复核心领域 | 可彻底重建 |
| 长期维护性 | 低到中 | 高 | 理论高，实际取决于完成度 |
| 回滚能力 | 高 | 高 | 低 |
| 对现有数据影响 | 小 | 可控迁移 | 大 |
| 测试建设 | 最小冒烟 | 核心链路测试矩阵 | 全新测试体系 |
| AI/语音 | 保留现状并做降级 | 重构为轻量模型、规则知识和适配器 | 全部重做 |
| 适合本项目 | 只能用于极短期抢救 | 最符合目标 | 不适合当前截止时间 |

## 3. A 档：保守收敛

### 3.1 范围

- 以现有 Flutter 页面和 Express controller 为主，不调整目录边界。
- 修复公开注册 ADMIN、弱密码重置、默认密钥等 P0。
- 修复订单事务和同步跨用户问题。
- 隐藏或删除明显凑数入口。
- 将首页、交易、AI 页和村级看板做一次视觉打磨。
- 增加少量冒烟测试和一条比赛启动命令。

### 3.2 优点

- 工期最短，最容易在早期 9 月截止前完成。
- 对当前代码和数据影响最小。
- 适合只求“能稳定演示”的紧急情况。

### 3.3 缺点

- 1000 行级 Flutter 页面、静态全局服务和 controller 直连 Prisma 会继续存在。
- 路由、搜索、助手词典和管理台目录仍需多处手工同步。
- 新增 2～3 名成员后，代码理解和并行修改成本仍然很高。
- 评委追问架构时只能解释为“做了安全修复和界面优化”，技术重构深度不足。

### 3.4 适用条件

只有在比赛时间提前到 3 周以内，或用户明确要求停止结构调整时，才退回 A 档。

## 4. B 档：渐进式领域重构（推荐）

### 4.1 范围

- 保留 Flutter、Express ESM、Prisma、SQLite 和模块化单体。
- 先建立测试、安全和数据基线，再逐条迁移核心链路。
- 后端从 `router → controller → prisma` 逐步变为 `controller → application service → repository`。
- Flutter 从页面直连 API 逐步变为业务纵向切片和可注入依赖。
- 建立 `/api/v2`、OpenAPI、typed DTO 和单一能力注册表。
- 农产品交易作为第一个完整样板，再迁移 AI 植保、村级经营、农机、政策和防灾。
- AI 去除本地大语言模型硬依赖，改为轻量识别、规则知识、离线意图和可选云 Provider。
- 管理台从通用 CRUD 转为“参考数据可通用、领域状态走专用命令”。

### 4.2 优点

- 不需要重新学习或迁移整套技术栈。
- 每个里程碑都可以展示、测试、验收和回滚。
- 能形成评委可理解的技术故事：安全基线、领域模型、事务一致性、离线能力、AI 适配和自动化测试。
- 对一人开发和未来多人接手都更友好。
- 可以设置比赛截止线，时间不足时安全停止在稳定版本。

### 4.3 缺点

- 新旧结构会在一段时间内共存。
- `/api/v1` 与 `/api/v2` 过渡期间需要契约和兼容测试。
- 必须严格控制新增需求，否则容易拖长。
- 单人完成全部范围需要约 35～50 人日，若比赛在 9 月上旬，需要执行范围截止线。

### 4.4 评委展示价值

推荐方案能够形成三层展示：

1. **表层体验**：TripGo 低碳农业科技视觉、稳定动效、完整交易与 AI 流程。
2. **业务深度**：订单状态机、库存事务、农机冲突、政策审核、灾情闭环和区域权限。
3. **技术深度**：离线优先的比赛运行、轻量 AI、API 契约、数据库迁移、自动化测试、安全与可回滚发布。

## 5. C 档：全面重写

### 5.1 范围

- 重建 Flutter 工程或再次迁移新前端框架。
- 后端全面 TypeScript 化，可能同时更换数据库或 ORM。
- 重新设计全部 API、数据表、角色和管理台。
- 一次性重建测试、CI、部署和 AI 架构。

### 5.2 优点

- 可以获得最整齐的最终目录和契约。
- 不需要长期保留旧代码的兼容层。
- 如果有成熟团队和充足时间，长期架构上限最高。

### 5.3 缺点

- 现有功能和已验证流程几乎无法复用。
- 单人开发极易在比赛前只得到一个“架构漂亮但业务不完整”的半成品。
- Android 插件、离线语音、相机、APK 构建和管理台都要重新验证。
- 数据迁移和回滚难度最高。
- 当前 Vue 迁移后又恢复 Flutter 的历史已经证明，第二次大迁移风险不可接受。

### 5.4 结论

C 档不适合作为 2026 年 9 月比赛方案。若比赛结束后决定商业化，可基于 B 档的领域和契约成果重新评估，而不是现在启动。

## 6. 推荐方案的范围截止线

为避免 B 档变成失控的大重构，设置三条截止线。

### 6.1 比赛必达

- 当前 WIP 安全保存和新基线建立。
- 身份、权限、默认密钥、上传等 P0 安全闭环。
- 订单事务、库存和同步跨用户问题修复。
- Flutter 新信息架构和基础设计系统。
- 农产品交易完整闭环。
- AI 植保轻量离线方案与语音助手核心流程。
- 村级经营区域权限和稳定看板。
- 一键启动、种子重置、APK 真机和 3 分钟演示脚本。

### 6.2 应达

- 农机预约完整闭环。
- 政策查询、申请和管理台审核。
- 防灾上报、SOS、理赔与进度。
- 暗色、适老、WCAG 基线。
- `/api/v2`、OpenAPI 和自动回归矩阵。

### 6.3 可延期

- 乡村生活三个辅助能力的深度打磨。
- 设备沙盘的高级联动。
- Git 历史瘦身。
- Linux 完整部署自动化。
- 全项目 TypeScript 化。
- 比赛后依赖升级和商业化 HTTPS 部署。

## 7. 推荐结论

正式采用 B 档“渐进式领域重构”。

执行原则：

1. 先关闭安全和数据一致性 P0，再做视觉重构。
2. 先完成交易与 AI 双头牌，再扩展其它链路。
3. 每个里程碑必须可运行、可验收、可回滚。
4. 任何新增需求先进入 backlog，不插入当前里程碑。
5. 若时间不足，按“比赛必达 → 应达 → 可延期”顺序截断，不牺牲稳定性换功能数量。
