## 三、数据库、接口与一致性

### 15. 数据库最终选型

**推荐方案：**比赛版本继续使用 SQLite，不引入 PostgreSQL、Redis 或消息队列；为核心表补充唯一约束、索引和必要关系。

答：推荐方案

### 16. 数据库治理：migrations 与 db:push

- 正式 migrations：保存版本化 SQL，可审计、可重复升级，适合需要保留数据的数据库。
- `db:push`：直接将当前 schema 推到数据库，适合可丢弃的临时开发库，但不适合作为正式升级记录。

**推荐方案：**正式库统一使用 migrations；`db:push` 仅用于临时开发数据库。

答：推荐方案

### 17. 旧数据库兼容策略

**推荐方案：**启动升级前自动备份旧库，优先通过 migration 无损升级；失败时可以恢复。另提供一键重建完整种子数据的演示环境。

答：推荐方案

### 18. 时间存储方式

**推荐方案：**数据库统一存 UTC，App 和管理台统一显示 `Asia/Shanghai`。避免直接存本地时间造成排序、迁移和跨平台歧义。

答：推荐方案

### 19. 图片与附件模型

**推荐方案：**新增统一附件表，记录文件路径、MIME、大小、归属、创建时间等元数据；核心业务通过明确关联使用附件，不再继续扩散 JSON 字符串字段。

答：推荐方案

### 20. 离线写入范围

**推荐方案：**只保留农事记录、灾情/SOS 草稿和个人资料草稿的待发送能力；订单、支付、预约必须连接后端完成。

答：推荐方案

### 21. 同步冲突处理

第一轮选择“人工选择”，但让普通农户处理数据库冲突会显著增加 UI 和理解成本。

**推荐方案：**使用版本号或更新时间检测；冲突时保留服务端版本并生成待处理记录，由管理台处理。

答：推荐方案

### 22. 农机预约时间冲突

**推荐方案：**允许同一时间存在多个待确认申请，但机主确认预约时必须阻止同一农机发生时间重叠。

答：推荐方案

### 23. 订单状态和角色权限

**推荐方案：**

- 买家：支付、取消尚未接单的订单、确认收货。
- 卖家：接单、拒单、发货。
- 管理员：异常关闭、争议处理和受审计的纠错。
- 订单、物流和库存变化必须放入同一事务。

答：推荐方案

### 24. API v1/v2 与旧接口兼容

第一轮同时选择 `/api/v2`、双版本过渡和旧接口长期兼容，长期维护成本较高。

**推荐方案：**建设 `/api/v2`；`/api/v1` 只保留一个明确的过渡里程碑。新 App 完成切换且确认无外部依赖后，删除未使用的 v1 能力。

答：推荐方案

### 25. 断网比赛环境中的市场行情

**推荐方案：**使用带来源、数据日期和更新时间的本地权威数据快照，并支持管理台导入更新；禁止使用随机数伪装实时行情。

答：推荐方案

**推荐方案：**语音能力只以 APK 真机作为正式验收对象；Web 尽量提供基础能力，无法支持时明确提示。

**推荐方案：**先测 arm64 APK 的真实体积。如果超过 300MB，优先改为首次安装后从比赛机局域网下载语音模型，不直接删除语音能力。

答：比赛过程全程断网。。。

### 30. AI 与语音响应时间

第一轮的 30 秒更适合作为超时上限。

**推荐方案：**

- 普通交互反馈：小于 300ms。
- 普通 API：小于 1s。
- AI 首次可见反馈：小于 2s。
