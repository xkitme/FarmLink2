# 协作约定 · Claude（审查） × Codex（实现）

> 自本文件落地起，FarmLink 项目采用 review-driven 工作流：
> Claude 负责审查、设计、文档与修复清单；Codex 负责代码实现。
>
> 所有要求与修复方案沉到 `docs/`，Codex 直接读 docs 干活，不再依赖会话上下文。
>
> **2026-08 起扩展为「四轨协作」**：Backend / Flutter / Admin 三条产品轨并行开发，
> Integration 轨负责生成链、CI、变更范围门禁与统一验证。详见文末
> 「四轨协作与集成门禁」章节与 [116g-X-四轨协作与集成门禁.md](116g-X-四轨协作与集成门禁.md)。

## 角色分工

| 角色 | 职责 | 不做 |
|---|---|---|
| **Claude** | 代码审查（high effort recall）、架构与板块设计、`docs/` 维护、修复清单、产品口径校对、规划下一段范围 | 不直接写业务代码（除文档、配置、修订计划外） |
| **Codex** | 按 docs 工作单实现代码、跑 `flutter analyze` / `node --check`、提交 commit、回填工作单完成状态 | 不擅自扩大范围、不修改 docs 工作单本身（除标记 ✅ 完成 + 留实施备注） |
| **用户（你）** | 调度：转交任务给 Codex / 决定优先级 / 验收 | - |

## Codex 拿到任务后的标准动作

1. **先读 `docs/进度总览.md`**，确认当前位置和上一段的产出。
2. **打开对应 `docs/NN-*.md` 工作单**，按里面的「目标 / 改动 / 验收」逐项执行。
3. 实施过程中遇到不一致或需要扩大范围 → 不动手，回 chat 标记问题，等 Claude 出新清单。
4. 完成后：
   - 跑 `flutter analyze lib`（如改 App）/ `node --check`（如改后端）→ 必须全绿
   - 在工作单末尾追加「## 实施备注」一节，写改了哪些文件、是否偏离原方案、跑了什么验证
   - 在 `docs/进度总览.md` 把该段从 ⬜ 改为 ✅
   - 创建一次 commit（不 push，等用户确认）

### Commit message 规则（硬性）

- **从 commit `2983796d` 之后所有新 commit 必须用中文写**（项目里有初学者读不懂英文）
- 旧的英文 commit 不需要 rebase reword
- 推荐格式（参考最近合规示例）：

  ```
  fix: 完成 48a P0 review 修复
  feat: 新建 AI 双层会话页
  docs: 补 README 手动启动命令
  ```

- 仍保留前缀（`feat / fix / docs / chore / refactor`）便于解析；前缀后空格 + 中文描述
- 同一 commit 含 review 编号时直接写：`fix: 49a 修复 48a 部署阻断 H1/H2/H3`

## Claude 出工作单的格式

每段 docs/NN-xxx.md 至少包含：

- **目标**：一句话，对外口径
- **背景**：为何要做（关联到哪个 review finding / 用户反馈）
- **改动清单**：按文件分块，给出 before/after 片段或精确替换说明
- **接口契约**：涉及后端时列出 path / method / 字段；涉及前端时列出 widget 行为
- **验收**：可执行的检查项（命令 + 期望输出 / 视觉确认点）
- **不在范围内**：明确划线，防止 Codex 顺手扩大

## 产品口径硬约束

无论谁动手，文案 / UI / 提示一律按 `docs/产品呈现口径.md`：

- 对外定位「在线 SaaS 平台」
- 禁用：离线优先 / 断网可用 / 本地 AI / 本地兜底 / 单机部署
- 错误码 60002 对外文案：「服务暂时不可用，请稍后重试」

# 四轨协作与集成门禁（2026-08 起生效）

> 工作单：[116g-X-四轨协作与集成门禁.md](116g-X-四轨协作与集成门禁.md)
> 机器可读配置：`scripts/collaboration/lanes.json`（schemaVersion=2：branchMap + workorders 精确白名单）；范围检查器：`scripts/collaboration/scope-check.mjs`
> CI：`.github/workflows/ci-gates.yml`（PR + 手动触发；Node 固定 24.16.0）

## 1. 四条轨道、真实分支与工单白名单

> **CI 一律按「真实分支 → lane + workorder → 工单精确白名单」检查**（branchMap 见 lanes.json）。
> 下表「允许」列为 legacy 宽泛口径（仅本地 ad-hoc `--lane` 用），**不代表 CI 放行范围**；
> CI 放行范围以 `workorders` 中对应工单的精确白名单为准（116g-A/116h-A/116g-B/116g-X）。

| 轨道（workorder） | 真实分支前缀（branchMap） | 工单白名单要点 | 硬禁止 |
|---|---|---|---|
| **Backend** | `collab/116g-backend-*` → **116g-A** | backend/test/**、backend/package.json、116g-A 文档 + 8 个 controller/policy（**pending 未回填，backend/src/** 拒绝**） | 5 生成产物、backend/data/**、Prisma |
| **Flutter** | `collab/116h-flutter-*` → **116h-A** | main.dart、core/theme、core/router、design_system/**、pages/home/{shell,home}_page、widgets/common、app/test/**、pubspec*、116h-A 文档 | 5 生成产物（含 feature_catalog.dart）、backend/** |
| **Admin** | `collab/116g-admin-*` → **116g-B** | admin/src/{api,App.jsx,layouts,pages,components,policies,styles.css}、admin/test/**、admin/package*.json、116g-B 文档 | 5 生成产物（含 apiCatalog.js）、app/**、backend/src/** |
| **Integration** | `collab/integration-*` → **116g-X** | .github/**、scripts/collaboration/**、scripts/test/**、docs/协作约定.md、116g-X 文档（**docs 不再宽泛放行**） | backend/data/**、Prisma、业务代码 |

- 完整模式与 glob 语义以 `scripts/collaboration/lanes.json` 为准；本文表为速查。
- 越界判定顺序（workorder 模式）：globalForbid → 生成产物（非 integration）→ lane.forbid → 工单白名单 → 越界失败；未知/模糊分支、缺 base、分叉、脏工作树一律非零失败。

## 2. 每人独立 clone / worktree

- 每条轨道使用自己的 clone 或 `git worktree`，互不共享工作树。
- 开工前 `git fetch origin`；以最新 `origin/main` 为基线创建分支。
- 分支命名：`collab/<系列>-<lane>-<slug>`，如 `collab/116g-backend-data`、`collab/116h-flutter-shell`、`collab/116g-admin-safety`、`collab/integration-gates`；CI 的 branchMap 按前缀解析 lane 与 workorder，未知/模糊分支直接失败。

## 3. Git 硬规则

- **禁止直接 push main**；main 只能通过审查后的合并进入。
- **禁止 force push、rebase、reset 覆盖远端**；也禁止删除他人分支。
- **分叉即停止**：`git fetch` 后发现本地与远端分叉，立即停下报告，不得自行 merge/rebase 掩盖。
- 精确暂存，禁止 `git add -A` / `git add .`（按 A/M/D 清单逐文件 add）。
- commit 用中文描述，保持既有前缀（feat/fix/docs/chore/refactor）。
- 每批默认不 push，commit 等用户确认；push 状态以远端分支为准。

## 4. 生成产物只归 Integration

以下 5 个文件是生成产物，**任何 Agent 不得手改**，只能由 Integration 经生成器 `--write` 重建并提交：

1. `backend/src/contracts/capabilities.js`（gen-capabilities.mjs）
2. `backend/src/contracts/inventory-report.json`（inventory-routes.mjs）
3. `backend/src/modules/ai/services/assistant-catalog.generated.js`（gen-assistant-routes.mjs）
4. `backend/admin/src/apiCatalog.js`（gen-admin-api-catalog.mjs）
5. `app/lib/core/feature_catalog.dart`（gen-feature-catalog.mjs）

人工可编辑事实源 = `gen-capabilities.mjs` 内的 overlay 与 `scripts/collaboration/lanes.json` 等配置；生成产物是派生快照。手改生成产物来让 drift 门禁变绿 = 违规，直接打回。

## 5. 合并顺序

1. Backend → 2. Flutter → 3. Admin → 4. Integration（收口生成产物与验证）。
- Integration 每次集成前：fetch origin main → 记录 base hash → 核对各成员 commit 只动自己区块 → 发现跨区立即停止（不代修）→ 更新注册表事实源 → `--write` 重建 → 全部 `--check` → 全量验证 → 更新 docs 稳定事实。
- 集成负责人**只能根据已审查的完整 commit hash 集成**，不接受口头描述或缩写。

## 6. 每批报告字段（提交/PR 必填）

PR 模板 `.github/pull_request_template.md` 强制以下字段，缺失即挂起：

- BASE/HEAD 完整 40 位 hash；base 必须是 head 祖先
- A/M/D 精确文件清单（与 `git diff --name-status` 一致）
- 测试计数闭合（tests/suites/文件数，禁止只用 exit code）
- 安全影响；DB 指纹（SHA256/Size/Mtime）；Prisma diff
- 五个生成器 `--check` 结果（5/5）
- 截图（UI 变更必填）；回滚方式

## 7. DB / Prisma 安全要求

- **不修改 Prisma schema/migrations、不写正式库、不清空数据库**，除非用户与正式工作单明确授权（当前 `backend/prisma/**` 例外 workorders 为空 = 未授权）。
- 测试一律使用临时合成 SQLite（`backend/prisma/.test-*` 模式，见 116d §6），测试结束确定性清理。
- `backend/data/village.db` 零接触：指纹（SHA256/Size/Mtime）由 verify-all 前后比对保护。
- 全仓库额外 DB 文件必须为 0。

## 8. 截图批准门禁

- 任何 UI 行为/布局变更，提交前必须附截图（前后对照，标注视口与明/暗/适老覆盖）。
- 无截图 = 不合并；截图必须是真实运行产物，不得伪造。

## 9. 越界处理

- 任一成员提交触碰其他 lane 文件 → 集成负责人立即停止，**不自行替成员修复**，把精确文件清单退回该成员重做。
- scope checker（`scripts/collaboration/scope-check.mjs`）与 CI 的 `scope-check` job 是自动兜底：越界退出非零，PR 无法合并。
