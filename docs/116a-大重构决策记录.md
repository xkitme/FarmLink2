## 1. 产品定位

田园通的目标用户是农户，实际交付和验收对象是评委。产品设计必须同时满足两层要求：

1. **用户层**：界面、文案和流程都以正式农户产品呈现，不出现“比赛”“Demo”“开发中”“占位功能”等穿帮措辞。
2. **验收层**：评委应能在数分钟内理解产品价值，稳定完成关键操作，并在追问架构、安全、数据和 AI 时看到可信的技术依据。

因此，本次重构不是追求功能数量，也不是建设完整商业 SaaS，而是建设一套范围克制、闭环真实、演示稳定、技术解释成立的数字农业作品。

## 3. 正式产品范围

### 3.1 六条核心链路

按展示优先级排序：

1. 农产品交易。
2. AI 植保。
3. 村级经营。
4. 农机服务。
5. 惠农政策。
6. 防灾救助。

其中农产品交易与 AI 植保组成“双头牌”：交易体现完整业务闭环，AI 植保体现技术价值。

### 3.2 辅助能力

- 乡村生活只保留邻里互助、就业信息、环境反馈。
- 消息中心不占底部导航，只保留铃铛入口。
- 发布页继续作为一级底部导航入口。
- 设置中心现有能力保留，并在重构后统一状态、样式和权限。
- “全部服务”页面删除；全局搜索只搜索最终保留的功能、设置、帮助和当前用户记录。

### 3.3 设备能力

IoT 降为“设备沙盘”，作为次级能力存在，不进入六条主路径。用户界面不出现开发或比赛措辞；内部文档必须如实标记其数据为仿真数据，且不允许语音助手执行可能被误认为真实设备控制的高风险动作。

## 4. 核心闭环定义

### 4.1 农产品交易

商品列表 → 商品详情 → 库存校验 → 立即购买 → 模拟支付成功 → 订单记录 → 接单/取消/发货/收货 → 物流状态。

- 比赛版不接真实支付。
- “立即支付”后进入稳定、可重复的支付成功流程。
- 订单和库存写入必须使用事务并防止超卖。
- 买家、卖家、管理员各自只能执行允许的状态动作。

### 4.2 AI 植保

拍照 → 轻量识别 → 结果置信判断 → 处置建议 → 写入农事记录 → 7 天复查提醒。

- 不以本地大语言模型作为必需依赖。
- 识别模型必须经过本机基准测试后选择。
- 置信度不足时必须明确“不确定”，不得伪造病害结论。
- 建议由版本化规则知识库组织，并保留权威来源。

### 4.3 村级经营

- VILLAGE 只能查看所属区域。
- ADMIN 可以查看全部区域。
- 其它角色不得访问村级经营数据。
- 看板指标必须来自真实数据库聚合或带来源日期的固定数据快照，不使用随机数。

### 4.4 农机服务

农机浏览 → 详情 → 申请预约 → 机主确认 → 作业提醒 → 完成记录。

同一时间允许存在多个待确认申请，但确认时必须阻止同一农机产生重叠预约。

### 4.5 惠农政策

政策查询 → AI/知识助手统一问答 → 查看申请条件 → 上传材料 → 提交补贴申请 → 管理端审核 → 状态通知。

政策页不再重复建设独立 AI 功能点。

### 4.6 防灾救助

预警 → 灾情上报 → SOS 或理赔 → 处理进度 → 历史记录。

SOS 被视为高风险能力，必须二次确认、保存位置和联系人，并提供明确的人工紧急渠道说明。

## 7. 数据与接口决策

- SQLite 继续作为比赛交付数据库。
- 核心实体逐步补充 Prisma relations、唯一约束和索引。
- 数据库时间按 UTC 存储，界面按 `Asia/Shanghai` 显示。
- 迁移前自动备份，迁移失败可以恢复。
- 同时保留“一键重建完整演示故事数据”的能力。
- 图片迁移到统一附件模型，记录路径、MIME、大小、归属和创建时间。
- 离线待发送只覆盖农事记录、灾情/SOS 草稿和个人资料草稿。
- 同步冲突保留服务端版本，并进入管理端待处理记录。
- 市场行情使用带来源、日期和更新时间的本地权威快照，支持管理台导入更新。
- `/api/v2` 使用统一响应 `{ code, msg, data, timestamp, traceId }`。
- OpenAPI 作为 App、管理台和后端的目标契约来源。

## 8. 身份与安全决策

- 公开注册只能创建 FARMER。
- BIGFARMER、VILLAGE、EXPERT、MERCHANT 由 ADMIN 授予。
- ADMIN 只能通过初始化命令或受控管理流程创建。
- 客户端自注册 ADMIN 是重构前 P0 阻断项。
- 离线忘记密码验证码由管理台生成，5 分钟失效且只能使用一次；用户端不得直接获得后端生成值。
- `dev/demo` 可以包含种子账号，`release` 禁止默认密钥启动。
- 比赛包使用独立强密钥和固定演示账号。
- 移动端凭据迁入系统安全存储；管理台采用安全 Cookie 方案。
- 增加 token rotation、撤销、设备管理、强制下线、登录审计和暴力破解告警。
- 比赛局域网允许 HTTP；正式部署手册必须包含 HTTPS 方案。
- 上传只允许 JPEG、PNG、WebP，单文件不超过 10MB、单次不超过 9 张，并执行解码、重编码和 EXIF 清理。

## 9. 设计与演示决策

- 用户可见名称统一为“田园通”，不再展示 FarmLink。
- TripGo 低碳视觉继续作为主参考，保留森林绿、胶囊搜索和凸起发布按钮。
- 允许重做信息架构和整页布局。
- 动效数量可以丰富，但必须稳定克制，不能影响滚动、输入和弱设备性能。
- 所有整页视觉修改先提供截图，由用户确认后再提交。
- 支持暗色模式、适老模式和 WCAG 2.1 AA。
- 启动广告兼作首次引导，界面不出现比赛、演示、开发、占位等词。

## 10. 工程质量决策

- 最终验收必须包含浏览器 E2E 和 APK 真机。
- 六条主路径纳入自动回归矩阵。
- 在结构迁移前先补 characterization tests。
- 目标自动化覆盖率不低于 60%。
- 建立 Flutter、后端、管理台和辅助 Python 工具的统一 CI。
- 增加 lint、format、typecheck、依赖扫描、secret scan、视觉回归和自动无障碍检查。
- release APK 使用正式签名。
- 建立 dev/demo/release 环境配置、结构化日志、增强健康检查、备份恢复和一键验证命令。

## 11. 明确不做

- 不再迁移 Vue/Capacitor。
- 不拆微服务。
- 不引入 Docker。
- 比赛版本不迁 PostgreSQL。
- 不接真实支付。
- 不让公网模型成为断网演示依赖。
- 不把随机数、模板或仿真数据包装成实时权威结果。
- 不在当前重构中删除用户要求保留的旧 WIP。
- 不在用户明确回复“开工”前实施业务代码。

## 12. 实施时仍需通过小型技术验证确定的事项

以下事项不再影响总方向，但必须在对应里程碑开始时用短周期 spike 决定：

1. 轻量植保识别模型及运行位置（端侧或本机后端）。
2. Provider/状态管理是否继续 Provider，或在样板模块中迁移。
3. `/api/v2` OpenAPI 生成链路和 DTO 生成工具。
4. 附件表与旧 JSON 图片字段的兼容周期。
5. APK 打入语音模型后的真实体积、冷启动和安装时间。

以上 spike 必须形成 ADR 补充记录，不能在实现过程中无记录地改变架构。
