# 104 · 语音助手「又生成第二个答案」根因修复（TTS 回声自激环）

## 目标
doc103 去掉了命令回执第二轮 LLM，但用户重打 APK 后**仍**报：悬浮语音助手一次指令出**两个答案**，且「上一个输出气泡还保留着」。需找真正根因并修复。

## 背景 / 根因
环境=APK 模拟器，且用户同时报「TTS 有噪音」——说明 TTS 在该环境确实出声并可能被麦克风采集。三点拼合指向**语音回声自激环**：

1. 助手朗读完答案 → `_submitRecognized` 的 finally 自动重开麦聆听；
2. 麦克风录到**助手自己刚朗读的 TTS 声音**（`offline_stt_io.dart` 的 `RecordConfig` 里 `echoCancel:false / noiseSuppress:false`，模拟器又无硬件回声消除）；
3. sherpa 把这段 TTS 转成文字 → 静音后自动提交 → 助手**再回答一次**（第二个答案）。「上一个气泡还保留着」正是第二轮处理时第一轮答案仍显示。

为什么 doc102 的「只播一次」没堵住：那是收敛**播报次数**，本问题是**麦克风听到自己的朗读触发了新一轮 turn**，是另一条链路。

代码层最可能的触发点：`flutter_tts` 在 Android 模拟器上「播放完成」回调**提前触发**，使 `speakAndWait` 提前返回，于是在 TTS 仍在出声时就开了麦。

## 改动（两道防线，均保留连续聆听交互、低风险）
### 防线1 · TTS 保证播完再返回 `app/lib/core/tts_service.dart`
- `speakAndWait` 的等待分支：即使完成回调提前触发，也至少阻塞到**按字数预估的播放时长**（中文 ~260ms/字，clamp 800ms~60s）再返回。确保调用方开麦时 TTS 已真正静音，麦克风录不到朗读主体。
- 仅影响 `speakAndWait`（语音助手）；`speak`（聊天页点按朗读，不开麦）不受影响。

### 防线2 · 重听时挡回声 `app/lib/widgets/voice_assistant_layer.dart`
- 新增 `_muteAutoSubmitUntil`：每轮结束开麦前开一个 900ms 静默窗，期内的**自动**提交一律丢弃（吞掉残响尾音）；人工点「提交」不受限。
- 新增 `_looksLikeSpokenEcho(text)` + `_lastSpokenPlain`：朗读前记下本轮朗读纯文本；自动提交时若识别文本≈刚朗读的回复（是其子串，或长度与回复相当且 ≥80% 的字都在回复里）判为回声并丢弃。判据偏向「长且高度重叠=整段回声」，用户的新指令通常更短、内容不同，避免误伤真实指令。
- 两个判据**只作用于自动提交**（`auto==true`），命中即清空识别文本、继续聆听，不触发新一轮。

## 契约
- 不改接口、不改命令白名单、不改 STT 实现。纯客户端聆听/朗读时序与回声过滤。

## 验收
- `flutter analyze lib/widgets/voice_assistant_layer.dart lib/core/tts_service.dart` → No issues found。
- **需 APK 真机/模拟器复验**：说一条指令（如「打开实时行情」），助手应只回**一个**答案、只朗读一次、不再被自己的朗读触发第二轮。麦克风/TTS 回声链路无法无头测，最终以设备为准。

## 不在范围
- TTS 噪音本身（模拟器音频 HAL 伪影）：本批未改播放音质，仍建议真机复验。
- 若设备仍复现两个答案：退路是**取消「朗读后自动重开麦」**，改为用户点小球/提交再说下一句（彻底断环，代价是失去连续免提），留作下一步。

## 实施备注
- 预估播放时长偏保守（260ms/字）：完成回调可靠时几乎不增延时；回调提前触发时才补足等待，宁可多等一会也不让麦克风开在 TTS 上。
