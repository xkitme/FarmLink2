## 1. 背景与缺口

116f 完成后，项目进入四轨并行（Backend/Flutter/Admin 三条产品轨 + Integration 集成轨），但缺少：

1. **机器可读的文件所有权**：谁可以改什么路径没有自动检查，越界改动只能靠人工 review。
2. **生成产物保护**：`capabilities.js`、`apiCatalog.js`、`assistant-catalog.generated.js`、`feature_catalog.dart` 等 5 个生成产物没有「只许 Integration 重建」的硬约束。
3. **CI 门禁**：仓库尚无 `.github/workflows`；Backend/Admin/Flutter 的测试与 5 个 drift 门禁没有在 GitHub Actions 独立显示；失败无法自动阻断 PR。
4. **交接约定**：`docs/协作约定.md` 仍是双人（Claude×Codex）模式，未覆盖四轨分支命名、合并顺序、DB/Prisma 安全、截图批准、完整 hash 集成等要求。
5. **PR 模板**：缺失 BASE/HEAD hash、A/M/D、测试闭合、DB 指纹、Prisma diff、drift、截图、回滚等必填字段。

## 2. 本批目标（对外口径）

把「谁改了什么、能不能改、生成产物是否漂移、CI 是否全绿」全部变成**自动可检查**的规则；任何越界、手改生成产物、脏提交在 CI 上一律失败，人工审查只处理语义问题。

## 4. 实施内容与验收

### 4.1 lane 配置（lanes.json）

- 至少包含四条 lane：backend / flutter / admin / integration。
- 每条 lane 具备：`allow`（允许路径）、`forbid`（禁止路径）、`exceptions`（唯一工作单例外路径，`workorders` 数组为空 = 当前未授权任何工作单）。
- `generatedProducts`：5 个生成产物，对非 integration lane 一律硬失败。
- 判定顺序：globalForbid → 生成产物 → forbid → exceptions（需 `--workorder` 命中）→ allow → 越界。

**验收**：JSON 可被 scope-check.mjs 读取；四 lane 的允许/禁止/例外矩阵与本文 §3/§7 一致。

### 4.2 scope checker（scope-check.mjs）

- 参数：`--lane`、`--base`（必填）、`--head`（默认 HEAD）、`--repo`、`--workorder`、`--config`、`--json`。
- 变更来源：`git diff -z --name-status -M <base> <head>`，覆盖 A/M/D/R/C/T 等；`core.quotepath=false` + NUL 分隔，正确处理空格、中文路径；重命名同时检查新旧路径。
- 失败即非零：越界（退出 1，精确列出 路径+状态+原因）；分叉（base 非 head 祖先，退出 1）；脏工作树（退出 1）；未知 lane / 缺 base / sha 不可解析（退出 2）。
- 禁止把 generated 白名单放给业务 Agent（代码内硬编码生成产物检查）。
- checker 本身只读：不写文件、不改 .git、不碰工作树。

**验收**：`node --test scripts/test/scope-check.test.mjs` 25/25 全绿；四 lane 各一次合法样例 + 一次越界样例 CLI 实测；检查前后文件内容与 mtime 不变。

### 4.3 CI（ci-gates.yml）

- 触发：`pull_request` + `workflow_dispatch`；`permissions: contents: read`（最小化，无可写 token、不读 secrets、不上传任何产物）。
- `concurrency` 按 ref 分组 + `cancel-in-progress: true`；每个 job 有 `timeout-minutes`。
- Job 拆分独立显示：scope-check、Backend tests、Admin test+build、Flutter analyze+test、backend-drift（**5 个 drift 步骤各自独立步骤名**：inventory-routes / gen-capabilities / gen-admin-api-catalog / gen-assistant-routes / gen-feature-catalog）。
- scope-check job 按分支前缀选 lane（collab/backend\* → backend，collab/flutter\* → flutter，collab/admin\* → admin，collab/integration\* → integration，其他 → 报错退出）。
- 任一 job/step 失败必须传播为 workflow 失败（无 continue-on-error、无 `|| true`、无空 job）。
- 第三方 action 全部固定 commit SHA：checkout `11bd7190...`（v4.2.2）、setup-node `49933ea5...`（v4.4.0）、flutter-action `1a449444...`（v2.23.0）。
- CI 不写 `backend/data/village.db`；CI 测试库为临时合成库（沿用 backend 测试既有模式），不留库文件。
- 本地 verify-all（依赖本机 Flutter 绝对路径）无法直接进 CI → **不降级 verify-all**，拆出等价的 CI 子门禁（backend-tests / backend-drift / admin-test-build / flutter-analyze-test / scope-check），差异见 §8。

**验收**：YAML 静态校验通过；每 job 权限/超时/失败传播符合上述；无 artifact、无写 token。

### 4.4 PR 模板

必须包含：BASE/HEAD 完整 hash（base 必须是 head 祖先）；A/M/D 精确清单；测试计数闭合（tests/suites/文件数，禁 exit code 代替）；安全影响；DB 指纹（SHA256/Size/Mtime）；Prisma diff；5 个生成器 `--check` 结果；截图（UI 变更必填）；回滚方式；自检清单。

### 4.5 协作约定更新

见 §3.2；覆盖独立 worktree、分支命名、禁止 push main、禁止 force/rebase/reset、分叉停止、生成产物仅 Integration 更新、合并顺序、每批报告字段、DB/Prisma 安全、截图批准门禁、集成负责人只按已审查完整 hash 集成。

### 10.3 本地/CI 差异与说明

1. **EOL 环境差异（本机修复，非仓库改动）**：本机全局 `core.autocrlf=true` 使检出文件为 CRLF，而生成器与提交产物为 LF（HEAD blob 实测 0 CRLF）→ 五个 drift 门禁初始失败。修复：仓库本地 `core.autocrlf=false` + 对 5 个生成产物执行 delete+checkout 重刷为 LF。未新增 `.gitattributes`、未改任何提交内容；CI（Linux）默认无 autocrlf，不受影响。
2. **verify-all 与 CI 映射**：verify-all 依赖本机 Flutter/Java 绝对路径，无法直接进 GitHub Actions → **未降级 verify-all**，拆出等价 CI 子门禁：`backend-tests`（= Backend tests）、`backend-drift`（= 5 个 drift 门禁独立步骤）、`admin-test-build`（= Admin tests + build）、`flutter-analyze-test`（= Flutter analyze + test，CI 用 flutter-action 固定 SHA 安装，本机无 Flutter 故本地该步失败）、`scope-check`（CI 独有变更范围门禁）。本地 Flutter/Java 缺失导致 verify-all exit 1 属环境差异，非门禁降级。
3. **第三方 action 固定 SHA**：checkout `11bd71901bbe5b1630ceea73d27597364c9af683`（v4.2.2）、setup-node `49933ea5288caeca8642d1e84afbd3f7d6820020`（v4.4.0）、flutter-action `1a449444c387b1966244ae4d4f8c696479add0b2`（v2.23.0），均经 `git ls-remote` 核实。
4. **CI 生效时机**：本批未创建 PR；workflow 随分支合入 main 后，对所有 `collab/*` PR 生效（PR 触发使用合并 ref 的工作流版本）。
