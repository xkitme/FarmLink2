# 分段 96 — 管理台「测试 DeepSeek 连接」503 修复 + antd 静态 message 上下文告警消除

> 用户在管理台「语音助手配置」页报：`POST /admin/ai-assistant/test` 返回 503，控制台同时刷 antd 告警「Static function can not consume context like dynamic theme. Please use 'App' component instead.」。本段修两件事：① 测试端点走与运行时同一条健壮 DeepSeek 调用路径，消除 ECONNRESET 导致的 503；② 全局 message 改用 App 上下文实例，消除告警并让弹层继承主题。

## 一、目标

- 管理台「测试 DeepSeek 连接」在 Key/模型/网络正常时稳定返回 200。
- 控制台不再出现 antd 静态 message 告警；message 弹层继承 ConfigProvider 主题色。

## 二、背景 / 根因

- **503**：`admin.controller.js` 的 `aiAssistantConfigTest` 用**自己的内联 `fetch`**，没有 `deepseek.service.js#deepseekGenerate` 里的两项关键缓解——`Connection: close`（规避 undici 复用对端已关闭的 keep-alive 连接）与建连阶段重试。逐层验证：同机 `curl https://api.deepseek.com/v1/models` 得 HTTP 401（**网络可达**），但 Node `fetch` 直接 `TypeError: fetch failed / ECONNRESET`——正是 doc 94 记录的 undici 死连接复用问题。运行时语音助手走 `deepseekGenerate` 正常，唯独这个测试端点漏了缓解 → 必挂 → `errors.offline`（60002→HTTP 503）。
- **antd 告警**：`request.js` 与 8 个页面用静态 `import { message } from 'antd'`。antd v5 下静态方法脱离 React 上下文，无法消费动态主题，故每次 `message.xxx()` 调用即告警。

## 三、改动

### A. 测试端点复用健壮路径
- `backend/src/modules/platform/admin.controller.js`：`aiAssistantConfigTest` 删除内联 fetch，改调 `deepseekGenerate({apiKey, baseUrl, model, prompt:'回复 ok…', temperature:0, thinking, timeoutMs:20000})`。`deepseek-empty-content`（思考模式可能 content 空）视作「已连通」返回 200，其余异常仍走 `errors.offline`。新增 `import { deepseekGenerate }`。

### B. 全局 message 走 App 上下文
- 新增 `backend/admin/src/api/feedback.js`：导出代理 `message`（success/error/warning/info/loading/open/destroy）+ `setFeedbackMessage(instance)`；真实实例由 Bridge 注入，未挂载时退化为 no-op（不抛错）。
- `backend/admin/src/main.jsx`：在 `<AntApp>` 内挂 `<FeedbackBridge/>`，用 `AntApp.useApp().message` 经 `useEffect` 注入 `setFeedbackMessage`。
- `request.js` + 8 个页面（Login/AiAssistantPage/AiOpsPage/ApiDebugPage/ApiSwitchPage/ResourcePage/SeedDataPage/SiteImagePage）：把 `message` 从 `'antd'` 导入改为 `'../api/feedback.js'`（`request.js` 为 `'./feedback.js'`）。调用点 `message.xxx(...)` 不变，仅换来源。`Modal` 等组件式用法不受影响（无 `Modal.confirm` 静态调用）。

## 四、契约

- 接口与响应码不变；测试端点成功 `{ok,model,latencyMs,sample}`，失败仍 `errors.offline`/`errors.param`。
- 无 Key 仍 `errors.param('尚未配置 DeepSeek API Key')`。

## 五、验收

- `node --check src/modules/platform/admin.controller.js` 通过。
- 服务端复跑：`deepseekGenerate` 直连 DeepSeek `OK 648ms model=deepseek-v4-flash sample="ok"`（内联 fetch 同条件 ECONNRESET）。
- 对运行中的 :8000（admin/123456）`POST /admin/ai-assistant/test` → **HTTP 200**「DeepSeek 连接正常」`latencyMs 567, sample "ok"`。
- 管理台 `npm run build` 成功。
- 浏览器实测（:5173 登录 admin/123456 → 语音助手配置 → 测试连接）：控制台 **0 error、无 antd 静态 message 告警**（仅剩无关的 React Router future-flag 提示与 favicon 404）；登录与测试的 `message.success` 均正常弹出。

## 六、不在范围

- 不改 `deepseekGenerate` 本身、不改语音助手运行时调用链。
- 不动 React Router future-flag 告警与 favicon 404（无关历史项）。
- 未给测试端点加 max_tokens 限制（`deepseekGenerate` 不限，避免推理吃空 content）。

## 七、实施备注

- 教训：同一上游有两条调用路径（运行时 `deepseekGenerate` vs 测试内联 fetch）时，缓解措施容易只加在一条上。已统一到 `deepseekGenerate` 单一来源。
- `curl` 走系统栈能连、Node undici 复用死连接报 ECONNRESET，是区分「网络不通」与「连接复用 bug」的关键判据。
